## [3.2.0rc1] - 2026-10-28 (pre-release)

Release candidate for 3.2.0 (git tag `v3.2.0-rc.1`, PEP 440 version `3.2.0rc1`). The latest stable release is still `v3.1.1`: the README and the installation docs keep documenting it until the final 3.2.0 release, while the installers pin the release candidate tag. The installer start message says "release candidate" when the tag contains `-rc`.

### What enters 3.2
- Setup and onboarding: `rapid setup` conductor and user-level `/rapid-init`.
- Per-component stack catalog and topologies.
- Infrastructure services with `compose.yaml`.
- Security baseline and security CI.
- Modular monolith with `rapid arch check`.
- `review_drafts` and `rapid setup doc <id> --confirm`.
- Seed stories.
- T001 scaffold task in an empty repository.
- `rapid deploy`.
- `rapid shortcuts install --global`.

### Known issues
- H-04: `--confirm` leaves a `.bak` copy.
- H-07: there is no API-only topology.
- H-09: `--global` does not install the hooks.
- H-10: messages mix Spanish and English.

The detail of each change is listed below, under the former `[Unreleased]` heading.

### Detailed changes

### Added
- Per-component stack catalog: `templates/stacks/<component>/<id>.json` and `.md`. Backend: `python-fastapi`, `python-django`, `node-nestjs`, `node-fastify`, `go`, `rust-axum`, `ruby-rails`, `dotnet-aspnetcore`, `java-spring-boot`, `kotlin-spring-boot` and `php-laravel`. Frontend: `react-vite`, `nextjs`, `angular`, `vue-vite`, `nuxt`, `svelte-vite`, `sveltekit` and `astro`. Each entry carries the eleven qualitative `factors` (performance, memory, cold start, concurrency, typing, productivity, learning curve, maintainability, ecosystem maturity, job market and hosting), each with its official `sources`, plus `fits`, `avoid_if`, `default_test_command`, `package_manager` and `supported_services` (service engines with their driver). An incomplete entry is `RAPID1401`. Page `docs/concepts/stacks.md`.
- Topologies declare their `components` (`front-end-only`: `frontend`; `fullstack-separated`: `frontend` and `backend`; `fullstack-baas`: `frontend` and `baas`; `doc-site`: `docs`) and `SetupState.stacks` stores one stack per component. `choose_stack` is emitted per component (with `factors`, `factor_sources`, `questions` and the `instruction` on how to recommend) and `rapid setup set stack <id> [--component frontend|backend]` fills one or, if the framework covers several (`nextjs`, `nuxt`, `sveltekit`, `ruby-rails`, `python-django`, `php-laravel`), all of them. The questions in `stack-questions.json` are now: team languages, load and latency, infrastructure budget, real time, compute-intensive or AI/ML, maintenance horizon and organizational constraints.
- Compatibility: a `setup.json` with `stack` is read as `stacks` without losing anything (`python-api` → backend `python-fastapi`; `python-ai` → `python-fastapi` and `ai: yes`; `nodejs-ai` → `node-fastify` and `ai: yes`; `web-modern` → `nextjs`; `frontend-creative` → `react-vite` with the creative profile; `docs-modern` and `generic` are kept) and the previous ids are still accepted in `rapid setup set stack` and `rapid init --stack`. A finished onboarding is not reopened because of a component that never had to decide. Guide `docs/guides/setup-json-migration.md`.
- Idiomatic architecture per language (extends the modular monolith): `architecture.json` gains `roles`, `module_pattern`, `public_contract`, `public_policy`, `public_dirs`, `namespace_root`, `aliases`, `pure_layer`, `delegate`, `complementary` and `rules` (one per component; `backend/` and `frontend/` when they are different stacks). `architecture.md` is generated with the names of the chosen language (`internal/<m>/` and `http/`, `app/`, `domain/`, `store/` in Go; packages in Spring; `<M>.Api`/`<M>.Contracts` projects in .NET; `features/<f>/` with `ui/`, `state/`, `data-access/` and `model/` in the frontends) and a final table mapping each name to its canonical responsibility. Page `docs/concepts/architecture.md`.
- Multi-language `rapid arch check`, without executing code or adding dependencies: Python, TypeScript and JavaScript (including the script of `.vue`, `.svelte` and `.astro`), Go, Java, Kotlin, C# (`using` and `.csproj` references), Rust and PHP. Ruby on Rails delegates to `bin/packwerk check` and, without packwerk, it warns and does not give the gate a PASS. The scaffold names the ecosystem's complementary test (Spring Modulith, Deptrac, NetArchTest, packwerk).
- Per-language security CI: `templates/ci/{go,rust,ruby,dotnet,java,kotlin,php}-security.yml` (govulncheck, cargo audit, bundler-audit and brakeman, `dotnet package list --vulnerable`, GitHub dependency graph review, composer audit), with gitleaks and semgrep, all actions pinned by SHA. A project with two languages writes a second workflow (`rapid-security-<language>.yml`) without repeating the secret scan. `set services` is validated against the backend stack (`RAPID1402` with the engines it does support) and the driver in `.env.example` and `tech-stack.md` comes from its `supported_services`.
- The scanner detects the new frameworks from their manifests (`go.mod`, `Cargo.toml` with `axum`, `Gemfile` with `rails`, web `*.csproj`, `pom.xml` or `build.gradle(.kts)` with Spring Boot, `composer.json` with Laravel, `angular.json`, and `vue`, `nuxt`, `svelte`, `@sveltejs/kit`, `astro`, `@nestjs/core` and `fastify` in `package.json`) and proposes the stack of each component.
- Infrastructure services as a recorded decision, not part of the stack: `templates/services/<engine>.json` catalog (postgresql, mysql, mariadb, mongodb, redis, valkey, rabbitmq and kafka in KRaft; official image with pinned major version, ports, variables, healthcheck, volume, connection variable, per-language drivers and sources, validated with `RAPID1401`), the `choose_services` onboarding decision (after `brief` and `business`) and `rapid setup set services <role>:<engine>[@now|@later],...` (`none` is valid; `RAPID1413` for an unknown or incompatible role or engine, `RAPID1402` if the stack does not support the engine). `SetupState.services` is stored in `setup.json` (optional). Changing it after `finish` applies immediately. Stacks only suggest a minimum (`suggested_services`). Page `docs/concepts/infrastructure-services.md`.
- `setup finish` writes `compose.yaml` (one service per `@now`, pinned image, healthcheck, named volume, ports on `127.0.0.1`), `.env.example` and `.env` in `.gitignore` in an empty repository; when moving from `@later` to `@now` it only adds what is missing without modifying what exists, and an unreadable YAML is left untouched with a warning. `tech-stack.md` takes the database and driver from the decision. The person action `local-services` (`docker compose up -d`) appears in `setup finish`, `rapid status` and `rapid validate` while the `compose.yaml` exists. The scaffold task asks for configuration from `.env.example`, migrations, unit tests without external services, a marker for integration tests (`gate.tests` passes without Docker) and a non-root multi-stage Dockerfile with a healthcheck.
- `ARCHITECTURE.md` requires the `Servicios de infraestructura` section and `DATA_MODEL.md` the conditional `Base de datos local` section when there is a `database` service (`RAPID1403`); the question banks support conditional sections.
- Optional document `docs/DEPLOYMENT.md` (the last one in onboarding, with the sections `Destino`, `Configuración y secretos`, `Servicios gestionados` and `Verificación y reversión`; first question: platform) and templates `templates/deploy/{aws,azure,vercel,render,railway,dokploy}.md` with official sources (they replace the AWS one; Vercel is for frontend and functions, not for an API with persistent connections). Guide `docs/guides/deployment.md`.
- A repository without commits no longer blocks a run that the policy requires to be isolated: the contract records `isolation_waived: "no_commits"` (optional, omitted from all other contracts), keeps the human gates and `rapid start` warns about it. A repository with commits does not change.

- Security baseline in every project: `templates/security/baseline.md` generates `.rapid-os/standards/security.md` with imperative rules, each with its standard in brackets: OWASP ASVS 5.0.0 (L1 in MVP, L2 in Corporate), OWASP Top 10:2025 (A01-A10), OWASP API Security Top 10:2023 (API1-API10, API stacks only), NIST SSDF SP 800-218 (PO, PS, PW, RV), SLSA 1.2 (pinning of dependencies and actions; Corporate adds Build L2 and Source L2) and CWE/CVSS v4.0. The names come from the official sources and their URLs are kept in a comment. It replaces `corporate/security.md`; `default-security.md` still serves `rapid start hardening` without an archetype. `mvp/coding-rules.md` no longer allows `any` and states that speed never lowers the baseline. Page `docs/concepts/security-baseline.md`.
- `ai` onboarding decision (`choose_ai`, after the archetype; `rapid setup set ai yes|no`): with `yes`, `security.md` includes the AI section (OWASP Top 10 for LLM Applications 2025 and Top 10 for Agentic Applications 2026). `python-ai` and `nodejs-ai` do not ask. A `setup.json` without the field is read as undecided while it is not finished, and as `no` if it is.
- Security CI written by Rapid OS: when closing the onboarding of an empty repository, `setup finish` writes `.github/workflows/rapid-security.yml` from `templates/ci/<python|typescript>-security.yml` (gitleaks, semgrep with the OWASP Top 10 rules, bandit or `pip-audit`/`npm audit`; Corporate adds SBOM and provenance), with all actions pinned by full SHA. It does not overwrite an existing one. It appears in the output of `finish` (`added_files` in `--json`) and is announced in `review_drafts` (`planned_files`).
- `rapid setup set archetype <id> --refresh` regenerates `security.md` and `coding-rules.md` with a `.bak` copy; `rapid doctor` warns with `RAPID1421` (WARNING) if `security.md` does not mention ASVS. `rapid init` no longer rewrites a hand-made `security.md`.
- Hardening mode: the spec template includes `findings` (`cwe`, `cvss_v4_vector`, `severity`, `standard_ref`) and the instruction to classify each finding with CWE and CVSS v4.0 and to cite the rule from `security.md`. The spec only keeps the fields of its schema, so the agent repeats each finding in `acceptance_criteria`.
- Modular monolith as the reference architecture: every project with a backend (`python-api`, `python-ai`, `nodejs-ai`, `web-modern`) starts with modules per business capability, layers inside each module (`api`, `application`, `domain`, `infrastructure`), a single public entry point per module and hexagonal only where justified. `rapid setup finish` and `rapid init` write `.rapid-os/standards/architecture.md` (the rule for the agent, with the stack tree, without an assumption banner) and `architecture.json` (the rule for Rapid OS); `docs-modern`, `frontend-creative` and `generic` do not receive it. Template in `templates/architecture/modular-monolith.md`. Page `docs/concepts/architecture.md`.
- `rapid arch check [--json]`: own verifier of the rule, with no new dependencies (Python with `ast`, TypeScript/JavaScript with regular expressions). It reports a `RAPID1420` violation for each layer that imports a layer it should not, module that imports anything other than another module's public entry point, `shared` that imports a module or `domain` that imports a forbidden library; exit 1 with violations, 0 without them, without modules or (with a warning) without `architecture.json`. In an existing project it only judges inside `modules_root`. The `__init__.py` of a Python module can only be empty or re-export its own `public.py` (`init_reexport`): otherwise, `from app.modules.pagos import Repo` reached an internal layer through the package. Only directories in `modules_root` count as modules. In a run's worktree (without `.rapid-os/`), with an active session whose contract includes `gate.architecture`, it reads the rule from the main project and analyzes the code of the current directory; if the run requires the gate and there is no rule, it ends with `RAPID1420` and exit 1.
- Machine gate `gate.architecture` (type `architecture_check`, post-execution, non-waivable) in the `feature`, `bugfix` and `refactor` contracts when `architecture.json` exists; `rapid next` proposes `rapid check --gate gate.architecture -- rapid arch check` and `rapid finish` does not give `PASS` without it. `rapid check` runs a leading `rapid` as the Rapid OS currently running. The evaluator's ruleset does not change, so existing reports keep their digest.
- The onboarding's `docs/ARCHITECTURE.md` requires the `Módulos` and `Reglas de dependencia` sections (`RAPID1403` if missing), with three new questions (business capabilities, hexagonal modules and dependency rules) and `max_chars` of 6000; `/rapid-init` starts from the modular monolith. The scaffold task of an empty repository asks for the structure of `architecture.md` (an example module with its four layers and its public entry point).
- `review_drafts`: before closing the onboarding, the person decides, document by document, whether a draft becomes a rule (`rapid setup doc <id> --confirm`) or stays as an assumption, with both consequences in the action payload (`drafts`, `consequences`, `commands`). New subcommand `rapid setup review --done` (with no unconfirmed drafts, because the person confirmed them all, it ends successfully without changing anything; `RAPID1413` only without `--done`); `rapid setup finish` with the review pending is `RAPID1407`; `drafts_reviewed` in `setup.json` is optional (an earlier file is read as `false`). A new draft or a `--reopen` reopens the review. `/rapid-init` summarizes each draft, runs `--confirm` only with explicit confirmation and lists at the end what was confirmed and what stayed as an assumption. Documented in `project-docs.md` ("Confirm or leave as an assumption"), `cli.md` and `first-project.md`.
- JSON sidecar per stack and topology (`templates/stacks/<id>.json`, `templates/topologies/<id>.json`) and the `rapid_os.domain.catalog` module that loads and validates them (`RAPID1401`). `default_topology_for_stack` and the compatibility of `validate_stack_topology` now read `compatible_topologies` and `default_topology`; the behavior of the 5 existing stacks does not change. A template without a sidecar is `RAPID1412` (warning) and is treated as compatible with all topologies except `doc-site`.
- `generic` stack: `rapid init` generates `tech-stack.md` with the language, package manager, framework and testing detected by the scanner and the rule of following the repository's conventions. `infer_stack` recognizes it by its exact header line (`# TECH STACK: GENERIC`).
- Question banks as data in `templates/setup/` (`docs/{brief,business,data-model,architecture}.json` and `stack-questions.json`), included in the sdist and wheel.

- `rapid setup next|show [--json]`: pure, read-only onboarding conductor (`rapid_os/domain/setup.py`, `rapid_os/orchestration/setup_conductor.py`, `rapid_os/adapters/setup_store.py`). It indicates the next decision (stack, topology, archetype, agents, test command, documents, finish) and derives the state from disk in projects initialized earlier; it never writes, not even `.rapid-os/setup.json`. Codes `RAPID1406` (invalid state), `RAPID1413` (invalid subcommand, key or value) and, reserved, `RAPID1400` (INFO "Valid setup").

- Onboarding documents in the context with their provenance: sources `doc.brief`, `doc.business`, `doc.data-model` and `doc.architecture` (they only count with `rapid-doc: <id>` frontmatter), assumptions banner for unconfirmed drafts, "ask, don't invent" line for skipped docs, and `doc.business` above `standards/business.md` (`standard.business` becomes skipped with the reason `superseded by doc.business`). Additive source types `product` and `data_model`. `rapid validate` emits `RAPID1400`, `RAPID1403`, `RAPID1404`, `RAPID1406`, `RAPID1408` and `RAPID1410`. Page `docs/concepts/project-docs.md`.

- `rapid setup set|stack|doc|finish`: the harness completes the onboarding with commands alone, and each one returns the next `SetupAction` in `--json`. `set stack|topology|archetype|agents|test-command` records the decision (`RAPID1413` invalid value, `RAPID1402` incompatible stack and topology); `stack --custom --file -` stores the harness's `tech-stack.md` with `Runtime`, `Framework` and `Testing` (`RAPID1409`); `doc <id> --source provided|drafted --file -` writes `docs/<FILE>.md` with frontmatter (`rapid-doc`, `source`, `status`, `sha256`) and a backup, validates sections and size only for `drafted` (`RAPID1403`/`RAPID1404` are a rejection, `RAPID1405` a draft over what a person provided without `--replace`); `doc <id> --skip|--confirm|--reopen|--from-legacy`; `finish` (`RAPID1407` if decisions remain) applies the standards and configuration, regenerates the agent files and is idempotent. The `business` `resolve_doc` includes `legacy_source` when there is a `standards/business.md` with content and `docs/BUSINESS_RULES.md` does not exist. The writes live in `rapid_os/orchestration/setup_apply.py`, without `sys.exit`.
- `rapid init --business-file <path>` (imports the business rules as `provided`) and `rapid init --skip-docs`. With `--yes` and without them, the documents stay `pending` and `init` ends with `Completa la documentación con /rapid-init o rapid setup next` ("Complete the documentation with /rapid-init or rapid setup next").
- `RAPID1414` (WARNING): `rapid init` warns, and `rapid doctor` reports, that `rapid` is not on the `PATH` when shortcuts or hooks are installed. It does not change the exit code.

- `/rapid-init [description]` (`templates/shortcuts/rapid-init.md`): the agent drives the whole onboarding with `rapid setup next --json` in a loop until `done`, proposes with reasons, writes drafts that it shows in full, and only runs `--confirm` if the person explicitly says so. It is a helper shortcut (not a mode one); `rapid-init` heads `SHORTCUT_NAMES`.
- `rapid shortcuts install|list|remove --global --harness <id> [--only <shortcut>]`: installs into the user's skills folder (`~/.claude/skills`, `~/.agents/skills`, `~/.cursor/skills`, `~/.gemini/config/skills`), with the official documentation cited in the code of each adapter. `vscode` has no documented path: `--global` gives `RAPID1413` and writes nothing. `--only` limits the command to one shortcut. `install.sh` and `install.ps1` offer to install the global `/rapid-init` when they finish (only with an interactive terminal, never by default).
- `rapid init` suggests `/rapid-init` (`$rapid-init` in Codex) when documents remain pending.
- `rapid approve` with a task in progress prints, after `RAPID1014`, ``<T> sigue en curso; espera a que el agente ejecute `rapid task done <T>`.`` (Spanish product output: "<T> is still in progress; wait for the agent to run `rapid task done <T>`") (same code and exit).
- Brief seed: the `author_spec` action of `rapid next` / `rapid start feature` (without a run or spec) gains the optional `seed` field (`source`, `confirmed`, `stories[]` with all the unchecked `- [ ] H001: ...` stories in order, `business_doc`, `data_model_doc`), omitted if there is no managed brief or no stories remain. `/rapid-feature` proposes the story that is best to start with and waits for confirmation, copies the relevant rules from `docs/BUSINESS_RULES.md` into `business_rules` and tags the spec with `story:<id>`; with an id (`H002`) it uses that story.
- `rapid finish` (verdict `pass` or `pass_with_waivers`) suggests `Marca H002 como hecha en docs/PRODUCT_BRIEF.md` ("Mark H002 as done in docs/PRODUCT_BRIEF.md") when the spec carries the tag `story:H002`; it never edits the brief (in `--json` the suggestion goes to stderr).
- `python-api` stack (FastAPI, Pydantic v2, SQLAlchemy 2 async, Alembic, PostgreSQL, pytest + httpx; no LangChain or CrewAI), compatible with `fullstack-separated` (default) and `fullstack-baas`. `infer_stack` recognizes it by `TECH STACK: PYTHON API`. `python-ai` remains only for "AI agents and data pipelines".
- New project (no source code outside `docs/` and hidden folders, and no tests): `rapid start feature` adds as the first task `T001: Scaffold mínimo con un test que pase` ("Minimal scaffold with a passing test"; the written tasks are renumbered to match the contract ids) and creates the contract without `gate.baseline`, with the optional field `baseline_waived: "empty_repository"` (omitted from the canonical content and from the digest of all other contracts). `rapid start` warns about the renumbering in the optional `notes` field of its output (`T001→T002`; `Nota: ...` in text mode) and `/rapid-feature` explains it to the person. `rapid status` and `rapid finish` show `Sin baseline: proyecto nuevo` ("No baseline: new project"). `bugfix`, `refactor` and `hardening` fail in a new repository with `RAPID1413` (`No hay código que arreglar|refactorizar|endurecer; usa /rapid-feature` — "There is no code to fix|refactor|harden; use /rapid-feature"). A repo with code and no tests keeps the baseline, and `run_baseline` suggests creating a passing test or using `research`.

### Changed
- Entry documentation with light commands: the home page, Getting Started, Your first project, Existing project and the five per-mode labs teach only installing, `/rapid-init`, `/rapid-<mode>`, `rapid approve` and `/rapid-next`. The v3 commands are folded into "Advanced mode" (nothing is deleted). The "First Governed Project" lab moves to the end as "Under the hood" (Advanced level) and the first one is Feature. New contract `test_beginner_routes_only_show_light_commands`: on those routes no command carries more than two flags.
- "Getting Started" section as a learning path in six pages, in reading order: Your first project, A project that already exists, When the agent stops (new: approve, reject, waive, view the status, cancel and read the verdict), How the spec is written, What the agent knows about your project and Next steps. The last four first explain in plain language and fold away the v3 commands; "Next steps" no longer ends in the 8-phase cycle, but in labs, which mode to use, teamwork and diagnostics.
- No heavy commands in the learning pages (home page, Getting Started, Labs, Installation and the shortcuts guide), not even folded: the per-mode labs keep only the shortcuts route, the initial state and the requirements; the walkthrough with v3 commands lives in a single place, the manual "Under the hood" walkthrough (How it works section), whose commands were rewritten with at most two flags (`rapid init --stack python-ai --yes` + `rapid setup set test-command`, `rapid spec create --title … --task …` + `rapid spec status <id> ready`) and remain executable (`test_tutorial_executable`). New contract `test_learning_pages_never_show_heavy_commands`.
- `install.sh` and `install.ps1`: the final question installs all shortcuts at user level (`rapid shortcuts install --global --harness <id>`), not only `/rapid-init`, so that `/rapid-feature` and the others exist when the onboarding closes without another command.
- The stack ids `python-api`, `python-ai`, `nodejs-ai`, `web-modern` and `frontend-creative` are no longer templates: they are aliases of the per-component stacks. With the `fullstack-separated` topology, `rapid setup set stack python-api` fills only the backend and the frontend is chosen separately. `fullstack-baas` no longer accepts a backend stack (its components are `frontend` and `baas`). `choose_stack` always brings `questions` and `instruction`.
- `rapid deploy --target <platform>` (or the positional argument) no longer writes `DEPLOY.md`: it prints the template and `rapid setup doc deployment --reopen`; an unknown platform is `RAPID1413`.
- The agent files that Rapid OS regenerates (`CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `INSTRUCTIONS.md`, `.agent/rules/constitution.md`) no longer leave `<file>.<timestamp>.bak` in the root: the previous copy goes to `.rapid-os/backups/`, only if the content changed, keeping the 5 most recent per file. `rapid init` and `rapid setup finish` add `.rapid-os/backups/` to `.gitignore`.
- The mode shortcuts and `rapid-approve` ask for approval only when `action.kind` is `await_human_approval` (`awaiting_human` lists the human gates from the start of the run), give the exact command with the gate id to run in another terminal and no longer suggest the `!` prefix.
- `rapid init` uses the same state and the same write logic as `rapid setup` (it writes `.rapid-os/setup.json`). The business section becomes one per document (brief, business, data model, architecture) with four options: import a file, write it in the terminal, leave it for the agent or skip it; without further input the document stays pending. The `TODO` scaffolding of `docs/` is removed (`create_optional_docs_scaffold`, `SPECS.md`) and `rapid init` no longer writes `standards/business.md` or stores business templates. Fixes that, after answering yes to "Import file?", an empty path or a directory gave `Is a directory`: it now asks again.
- `main` moves to the development version `3.2.0.dev0`. The stable release is still `v3.1.0` (branch `release/3.1`); the installers and the installation docs still point to that tag.

### Fixed
- Documentation synchronized with `3.2.0.dev0`: the `feature`, `bugfix` and `refactor` guides (and `governance-loop`, `architecture/orchestration` and `feature-lab`) explain `gate.architecture`; `hardening` explains findings with CWE and CVSS v4.0; the Claude Code, Cursor, VS Code and Antigravity integrations, `index`, `getting-started` and `existing-project` start from `rapid init` → `/rapid-init` → `/rapid-feature` with the draft review; the README uses the `rapid setup` flow (docs-modern + doc-site) and no longer says that `rapid deploy` writes `DEPLOY.md`.
- `diagnostics.md` documents every code that `rapid_os/` emits (`RAPID105–110`, `1105`, `200–208`, `300–311`, `400–405`, `500–502`, `900–909`) and removes `RAPID120` and `RAPID121`, which no code emits; a test fails if a `RAPIDxxx` in the code has no row or a row is not used.
- The installers only offer user-level `/rapid-init` if the installed `rapid` has `shortcuts install --global` (the stable version `v3.1.1` does not); the installation documentation explains it and `verification.md` includes `RAPID1414`.
- A finished onboarding does not reopen documents that did not exist when it was closed (e.g. `deployment`): `rapid setup next` returns `done` and the document is created whenever wanted with `rapid setup doc deployment --source ...` or `rapid deploy`; the same applies to any new decision in a finished project.
- Security workflows are named `rapid-security (<language>)` and are always written as `.github/workflows/rapid-security-<language>.yml`; a project with `rapid-security.yml` is left as is.
- In Go (and in root stacks with a public policy) the `architecture.md` table includes the public contract row; the `RAPID1420` message no longer repeats the parentheses.
- `rapid setup set archetype <id> --refresh` leaves its `.bak` copies in `.rapid-os/backups/` (same limit of 5 per file) and not next to `standards/`, which is what the agent reads.
- MySQL is pinned to `mysql:9.7` (LTS) and `tech-stack.md` says "MySQL 9.7 LTS" (source: https://docs.oracle.com/en-us/iaas/mysql-database/doc/mysql-server-versions.html); Kafka adds `start_period` (30s) to its healthcheck; the Azure template states that Azure Database for MariaDB was retired on September 19, 2025.
- The five `RAPID1301` warnings of run conduction suggest `rapid setup set test-command <cmd>` from a single constant (`TEST_COMMAND_FIX`).
- A folder without git reached PASS without the person knowing that `git init` was needed: `rapid setup finish` and `rapid init` create the repository (`ensure_git_repository`: `git init` and `symbolic-ref HEAD` to `main`, no commits; it never nests a repository inside another; without git installed it only warns). `/rapid-init` tells the person.
- Rapid OS works end to end inside the Codex sandbox on Windows without asking anything of the person: all its git commands go through a single gate (`rapid_os/orchestration/git.py`, `run_git`) with `-c safe.directory=<project root>` (only the root, never `*`) and `-c core.fsmonitor=false`. A test fails if a `["git", ...]` remains outside that module. What the person needs for their own git arrives as an action: `person_actions` (`git-safe-directory`, with the command `git config --global --add safe.directory <path>`) in `rapid setup finish`, `rapid setup next --json` (`done`) and `rapid doctor`, and the `rapid-init` and `rapid-status` shortcuts show it without running it. Documented in `docs/integrations/codex.md` (including the `sandbox = "unelevated"` alternative and its isolation cost). `RAPID1416` due to `untrusted` now only occurs with git older than 2.38 or with the repository above the project root.
- `ensure_git_repository` distinguishes "could not be created" from "was created with `git init` but setting the branch failed".
- `rapid finish --json` keeps stdout as the report only when it ticks the brief's story (the agent files it regenerates no longer write to stdout).
- A folder with a repository that git does not trust (`detected dubious ownership`) has its own state, `untrusted`, in `git_work_tree_state`: `setup finish` does not run `git init` and warns with `git config --global --add safe.directory <path>`, `rapid start` fails with `RAPID1416` and that same command, and `rapid finish` names it in `unverified_reason`.
- `rapid start` fails early with `RAPID1416` if the folder is not a git repository (before creating the run and before `RAPID1413`), instead of creating a run that cannot observe changes.
- `rapid finish` explains an `UNVERIFIED` caused by a lack of writes (`No se observaron cambios de archivos: <cause>` — "No file changes were observed: <cause>"; optional `unverified_reason` field in `--json`).
- `/rapid-feature` asks not to write a scaffold task in a new project: Rapid OS adds `T001`.
- `rapid approve` on Windows with stdin redirected to `NUL` (which reports `isatty() == True`) now fails with `RAPID1310` before touching the ledger, instead of reaching `RAPID1014`: `stdin_is_windows_nul()` tells `NUL` apart from a console using `GetConsoleMode`. The approval was already rejected; only the diagnostic changed.
- `rapid finish` sees changes in a repository without commits: with a null `start_head`, `file_change` records the files in the index and the untracked ones minus `start_untracked`, with the same artifact filter (`observed_changes(cwd, start_head | None, start_untracked)`). Before, there was no evidence and the verdict was `UNVERIFIED` on the empty folder → feature path.
- A run's harness no longer comes out as `cursor` in a project with `"tools": ["codex"]`: `detect_harness` uses the single supported harness in `tools` (source `config_tools`); with several it keeps the `RAPID1300` fallback and the warning lists them. No Codex marker is added: its official documentation only describes its own variables (`CODEX_HOME`, `CODEX_API_KEY`) and `CODEX_THREAD_ID` appears only in a GitHub discussion.
- Accents lost on Windows PowerShell: `/rapid-init` says to write the document to a temporary UTF-8 file and use `--file`; `rapid setup doc --source drafted` rejects a body with a `?` between two letters or at the start of a word (`vac?os`, `?xito`; `RAPID1415`) and with `provided` only warns.
- `rapid setup set` after `finish` applies the change immediately and leaves `finished=true`, without reopening the onboarding. The scaffold task of an empty repository without `test_command` says `rapid setup set test-command <cmd>`, and `RAPID1301` from `rapid task done` suggests that command.
- `rapid finish` with a PASS verdict ticks in `docs/PRODUCT_BRIEF.md` the story that the spec cites with the tag `story:<ID>` (only that line; backup in `.rapid-os/backups/`; `source`, `status` and draft untouched). `rapid finish --no-tick` keeps the suggestion. `/rapid-feature` asks for the `story:<ID>` tag.
- Codex CLI: the documentation explains that in the CLI `/` does not list the skills and that shortcuts are invoked with `$rapid-<mode>` (or from `/skills`); `/rapid-init` and `/rapid-status` indicate the `$` form for Codex.
- The `pipx install rapid-os` suggestions (a package that does not exist on PyPI) become `pipx install git+https://github.com/alyconr/Rapid-OS.git`.
- The `file_change` evidence (capability `repository.write`) no longer counts tool artifacts: `rapid finish` ignores paths with a segment `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.tox`, `.nox`, `node_modules`, `.venv` or `venv`, and files `*.pyc`, `*.pyo`, `.coverage` and `.coverage.*`, even if the project has no `.gitignore`. Before, running the tests left `__pycache__` and a task with no real changes came out `pass`; now, without changes, no `file_change` is recorded and the verdict is not `pass`. `rapid init` and `rapid setup finish` add `__pycache__/`, `*.pyc` and `.pytest_cache/` to an existing `.gitignore` (they never create it). The diff + untracked + filters logic lives in a single function (`observed_changes`), shared with the list of untracked files at the start of the run.
- `rapid init` suggested `python -m unittest discover` as the test command in JavaScript repositories with a `tests/` folder. Now a single function (`propose_test_command`) is used by `init` and `setup`: `npm test` if `package.json` has `scripts.test`, pytest if detected, and `unittest discover` only in Python projects with a tests folder; otherwise, no suggestion.
- Behavior fix: `rapid init --yes` without a scanner suggestion no longer chooses `web-modern` (Next.js) but `generic`.

## [3.1.1] - 2026-10-19

### Fixed
- Stable installers now put a real `rapid` executable on `PATH` instead of a shell alias (`install.sh`) or a PowerShell profile function (`install.ps1`). Shortcuts and Claude Code hooks run `rapid` from the agent's non-interactive shell (Git Bash on Windows), which sees neither, and failed with `rapid: command not found`. `install.sh` installs into `~/.rapid-os/.venv` and links `~/.local/bin/rapid`; `install.ps1` installs into `$HOME\.rapid-os\.venv` and puts `rapid.exe` in `$HOME\.rapid-os\bin` on the user `PATH`. Both remove the alias or function left by earlier installers (with a `.rapid-os.bak` backup).

## [3.1.0] - 2026-10-18

### Added
- **Porcelain layer**: `rapid start`, `rapid next`, `rapid check`, `rapid task`, `rapid attach`, `rapid finish`, `rapid approve`, `rapid status` and `rapid abort` drive a governed run on top of the v3 plumbing. A pure Conductor (`next_action`) asks the `BehavioralEvaluator` what is missing and returns a `NextAction`; the active run lives in `.rapid-os/session.json`. Evidence producers: `rapid:check`, `rapid:start`, `rapid:finish`, `rapid:attach`.
- **Behavioral ruleset v2**: `rapid check --expect fail --task <id>` records an expected failure (`expectation: "fail"`) that produces a `reproduction.<task>` assertion and does not count as a failing task or gate evidence (`RAPID1320`); review evidence produced by a `harness:*` producer cannot close a human gate.
- **Five engineering modes** with playbooks in `templates/modes/`: `feature`, `bugfix` (baseline before the red test, `check --expect fail` on `T001`), `refactor` (blocked when passing tests drop below the baseline), `hardening` (isolated git worktree with `rapid start --worktree`) and `research` (`rapid attach`, no mandatory tests).
- **Shortcuts**: `rapid shortcuts install|list|remove` and `rapid init --shortcuts` generate eight `/rapid-<mode>` shortcuts (`rapid-feature`, `-bugfix`, `-refactor`, `-hardening`, `-research`, `-next`, `-status`, `-approve`) for Claude Code, Codex, Antigravity, Cursor and VS Code from `templates/shortcuts/`, idempotent and with `.bak` backups (`RAPID1311`–`RAPID1318`). A `RAPID1321` warning flags harness selections that leave the same shortcut in two folders one tool reads.
- **Claude Code hooks**: `rapid hook stop|pre-tool` keep the agent working until a person is needed and deny reserved commands (`rapid approve`, `rapid abort`, `rapid run gate`, `rapid evidence add`) and edits inside `.rapid-os/`; installed with `rapid shortcuts install --hooks` or `rapid init --hooks` (`RAPID1337`–`RAPID1339`).
- `rapid approve` without arguments lists pending human gates; `--waive` (waivable gates only) and `--reject` (review outcome `changes_requested`) with `--reason`; `--reviewer` defaults to `git config user.name` (`RAPID1330`–`RAPID1336`).
- `docs/architecture/orchestration.md` and `docs/guides/shortcuts.md`.

### Changed
- **`rapid approve` hardened**: it requires a TTY, refuses `CLAUDE_CODE_CHILD_SESSION=1` and, new, refuses when any ancestor process is Claude Code (`RAPID1310`; `RAPID1319` in `rapid doctor` when the ancestry cannot be read). The ancestry check is best-effort: a process that detaches from its parent (double fork, `setsid`, `nohup … &`), a renamed `claude.exe` or a reused pid escape it. The rule is unchanged: a person approves in their own terminal.
- **Shortcuts JSON contract**: in `rapid shortcuts install --json` and `list --json`, `warnings` is a list of homogeneous objects `{code, message, ...}` (`RAPID1315`, `RAPID1316`, `RAPID1321`); the loose text warnings of `install --json` became objects with the same text in `message`.
- Package version is `3.1.0`; the installers and the installation docs resolve the `v3.1.0` tag.
- `rapid finish` on a run that already ended exits `0` only when the stored verdict is `pass` or `pass_with_waivers` and records no new evidence; a run without a report exits `1` with `already ended (<outcome>)`.
- Product boundaries now state what is executed: the plumbing runs nothing; the porcelain runs only the `test_command` of `.rapid-os/config.json` or the argv given to `rapid check`, creates a worktree only with `rapid start --worktree`, and never invokes agents or approves human gates.
- Documentation presents the shortcuts as the main flow and the v3 commands as advanced mode; new "Shortcuts and Orchestration" sidebar category and navbar entry; the unused `site/` Docusaurus template was removed.

### Fixed
- `rapid finish` text mode no longer fails with `AttributeError` and prints the report revision and verdict.
- Runs without a baseline gate (low-risk spikes) and isolated runs could never leave `prepared`.
- `rapid finish` no longer attributes to the run the untracked files that existed before `rapid start`.
- `rapid init --yes` without a scanner suggestion no longer picks the alphabetically first topology (`doc-site`) for every stack: the default topology is coherent with the stack (`doc-site` only with `docs-modern`, and `docs-modern` always with `doc-site`), so `rapid validate` no longer fails with `RAPID402`/`RAPID403`.
- `rapid init` (also with `--yes`) creates `.rapid-os/standards/security.md` from a minimal template when it does not exist, so `rapid start hardening` can create the run; the `RAPID1004` message now names the missing file and how to create it.
- `rapid start --spec-file` reuses a spec with the same identity and content when a previous start failed after creating it; with different content it exits with `RAPID1322` and suggests `rapid start <mode> --spec <id>` instead of an error without guidance.
- The `feature` playbook's `author_spec` instruction now says `rapid start <mode> --spec-file -` instead of `rapid spec create`.
- `rapid next` returns `blocked` with `rapid start --resume --worktree` when the contract requires an isolated workspace and the session has no worktree yet, like `rapid start`.
- `rapid start` and `rapid approve` report expected failures (a missing context source, a closed stdin) with a RAPID code instead of a traceback.

### Security & Hardening
- Defense in depth around human approval: TTY, session marker, process ancestry, typed confirmation, optional Claude Code hooks (including a guard against clearing the session variables) and `user`-only review evidence. These are best-effort controls, not cryptographic attestation.

  - 14-level source precedence hierarchy, character budget enforcement (`--max-chars`) with non-truncation guarantee for required sources, conflict detection across selected sources, and `RAPID700–RAPID705` diagnostics.

  - Multi-spec registry in `.rapid-os/specs/<spec-id>/` with `SpecRecord` (`spec.json`), authoring lifecycle (`draft`, `ready`, `archived`), and immutable `SpecRevision` snapshots (`revisions/0001/`, ...) with SHA-256 artifact digests (`requirements.md`, `tasks.md`, `acceptance.md`).

  - Deterministic `ExecutionPolicy` (`.rapid-os/policy.json`) and `ExecutionPolicyEvaluator` producing `PolicyDecision` (`ExecutionClass`, `RiskLevel`, `WorkspaceRequirement`, `GateRequirement`).
  - Immutable `ExecutionContract` (`contract.json`), compiled context snapshots, and append-only `RunState` ledger (`states/0001.json` .. `000N.json`) under `.rapid-os/runs/<run-id>/`.
  - CLI commands `rapid policy show|init` and `rapid run create|list|show|status|task|gate`, plus `RAPID1000–RAPID1014` validation diagnostics.
- **Phase 5 — Harness Capability Registry (`rapid harness`)**:
  - Canonical 11-capability catalog (`CANONICAL_CAPABILITY_DEFINITIONS`) across 8 categories, conservative built-in `HarnessProfile` definitions, and full-replacement project overrides in `.rapid-os/harnesses/<id>.json`.

  - Append-only `EvidenceRegistry` under `.rapid-os/evidence/<run-id>/` storing immutable `RunEvidence` records (`records/E001.json`, ...) and SHA-256/size-verified copied artifacts (`artifacts/E001/`, ...).

  - CLI commands `rapid evidence list|show|add|verify` and `rapid eval run|list|show`, plus `RAPID1200–RAPID1229` diagnostics.

  - PEP 517/518 `pyproject.toml` and `MANIFEST.in` providing the `rapid` console script entrypoint (`rapid_os.cli.main:main`) and bundled templates for wheel installations.

  - End-to-end governance loop, negative `UNVERIFIED` gate enforcement, cross-layer tampering defense-in-depth, CLI/docs Product Truth contract, and packaged template resolution test suite (`tests/test_v3_release_readiness.py`).
