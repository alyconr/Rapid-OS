## [Unreleased]

### Added
- Catálogo de stacks por componente: `templates/stacks/<componente>/<id>.json` y `.md`. Backend: `python-fastapi`, `python-django`, `node-nestjs`, `node-fastify`, `go`, `rust-axum`, `ruby-rails`, `dotnet-aspnetcore`, `java-spring-boot`, `kotlin-spring-boot` y `php-laravel`. Frontend: `react-vite`, `nextjs`, `angular`, `vue-vite`, `nuxt`, `svelte-vite`, `sveltekit` y `astro`. Cada ficha trae los once `factors` cualitativos (rendimiento, memoria, arranque en frío, concurrencia, tipado, productividad, curva de aprendizaje, mantenibilidad, madurez del ecosistema, mercado laboral y hosting) cada uno con sus `sources` oficiales, además de `fits`, `avoid_if`, `default_test_command`, `package_manager` y `supported_services` (motores de servicios con su driver). Una ficha incompleta es `RAPID1401`. Página `docs/concepts/stacks.md`.
- Las topologías declaran sus `components` (`front-end-only`: `frontend`; `fullstack-separated`: `frontend` y `backend`; `fullstack-baas`: `frontend` y `baas`; `doc-site`: `docs`) y `SetupState.stacks` guarda un stack por componente. `choose_stack` se emite por componente (con `factors`, `factor_sources`, `questions` y la `instruction` de cómo recomendar) y `rapid setup set stack <id> [--component frontend|backend]` llena uno o, si el framework cubre varios (`nextjs`, `nuxt`, `sveltekit`, `ruby-rails`, `python-django`, `php-laravel`), todos. Las preguntas de `stack-questions.json` ahora son: lenguajes del equipo, carga y latencia, presupuesto de infraestructura, tiempo real, cómputo intensivo o IA/ML, horizonte de mantenimiento y restricciones de la organización.
- Compatibilidad: un `setup.json` con `stack` se lee como `stacks` sin perder nada (`python-api` → backend `python-fastapi`; `python-ai` → `python-fastapi` y `ai: yes`; `nodejs-ai` → `node-fastify` y `ai: yes`; `web-modern` → `nextjs`; `frontend-creative` → `react-vite` con el perfil creativo; `docs-modern` y `generic` se mantienen) y los ids de antes se siguen aceptando en `rapid setup set stack` y `rapid init --stack`. Un onboarding terminado no se reabre por un componente que nunca tuvo que decidir. Guía `docs/guides/setup-json-migration.md`.
- Arquitectura idiomática por lenguaje (extiende el monolito modular): `architecture.json` gana `roles`, `module_pattern`, `public_contract`, `public_policy`, `public_dirs`, `namespace_root`, `aliases`, `pure_layer`, `delegate`, `complementary` y `rules` (una por componente; `backend/` y `frontend/` cuando son stacks distintos). `architecture.md` se genera con los nombres del lenguaje elegido (`internal/<m>/` y `http/`, `app/`, `domain/`, `store/` en Go; paquetes en Spring; proyectos `<M>.Api`/`<M>.Contracts` en .NET; `features/<f>/` con `ui/`, `state/`, `data-access/` y `model/` en los frontends) y una tabla final que mapea cada nombre a su responsabilidad canónica. Página `docs/concepts/architecture.md`.
- `rapid arch check` multilenguaje, sin ejecutar código ni dependencias nuevas: Python, TypeScript y JavaScript (incluido el script de `.vue`, `.svelte` y `.astro`), Go, Java, Kotlin, C# (`using` y referencias de `.csproj`), Rust y PHP. Ruby on Rails delega en `bin/packwerk check` y, sin packwerk, avisa y no da PASS al gate. El scaffold nombra la prueba complementaria del ecosistema (Spring Modulith, Deptrac, NetArchTest, packwerk).
- CI de seguridad por lenguaje: `templates/ci/{go,rust,ruby,dotnet,java,kotlin,php}-security.yml` (govulncheck, cargo audit, bundler-audit y brakeman, `dotnet package list --vulnerable`, revisión de dependencias del grafo de GitHub, composer audit), con gitleaks y semgrep, todas las acciones fijadas por SHA. Un proyecto con dos lenguajes escribe un segundo workflow (`rapid-security-<lenguaje>.yml`) sin repetir el escaneo de secretos. `set services` se valida contra el stack del backend (`RAPID1402` con los motores que sí soporta) y el driver de `.env.example` y de `tech-stack.md` sale de su `supported_services`.
- El escáner detecta los frameworks nuevos por sus manifiestos (`go.mod`, `Cargo.toml` con `axum`, `Gemfile` con `rails`, `*.csproj` web, `pom.xml` o `build.gradle(.kts)` con Spring Boot, `composer.json` con Laravel, `angular.json`, y `vue`, `nuxt`, `svelte`, `@sveltejs/kit`, `astro`, `@nestjs/core` y `fastify` en `package.json`) y propone el stack de cada componente.
- Servicios de infraestructura como decisión registrada, no del stack: catálogo `templates/services/<motor>.json` (postgresql, mysql, mariadb, mongodb, redis, valkey, rabbitmq y kafka en KRaft; imagen oficial con versión mayor fijada, puertos, variables, healthcheck, volumen, variable de conexión, drivers por lenguaje y fuentes, validado con `RAPID1401`), decisión `choose_services` del onboarding (después de `brief` y `business`) y `rapid setup set services <rol>:<motor>[@now|@later],...` (`none` es válido; `RAPID1413` para un rol o motor desconocido o incompatible, `RAPID1402` si el stack no soporta el motor). `SetupState.services` se guarda en `setup.json` (opcional). Cambiarlo después de `finish` se aplica al instante. Los stacks solo sugieren un mínimo (`suggested_services`). Página `docs/concepts/infrastructure-services.md`.
- `setup finish` escribe `compose.yaml` (un servicio por `@now`, imagen fijada, healthcheck, volumen con nombre, puertos en `127.0.0.1`), `.env.example` y `.env` en `.gitignore` en un repositorio vacío; al pasar de `@later` a `@now` solo añade lo que falta sin modificar lo existente, y un YAML ilegible se deja intacto con un aviso. `tech-stack.md` toma la base de datos y el driver de la decisión. La acción de persona `local-services` (`docker compose up -d`) aparece en `setup finish`, `rapid status` y `rapid validate` mientras exista el `compose.yaml`. La tarea de scaffold pide configuración desde `.env.example`, migraciones, pruebas unitarias sin servicios externos, un marcador para integración (`gate.tests` pasa sin Docker) y un Dockerfile multi-stage no root con healthcheck.
- `ARCHITECTURE.md` exige la sección `Servicios de infraestructura` y `DATA_MODEL.md` la condicional `Base de datos local` cuando hay un servicio `database` (`RAPID1403`); los bancos admiten secciones condicionales.
- Documento opcional `docs/DEPLOYMENT.md` (el último del onboarding, con las secciones `Destino`, `Configuración y secretos`, `Servicios gestionados` y `Verificación y reversión`; primera pregunta: plataforma) y plantillas `templates/deploy/{aws,azure,vercel,render,railway,dokploy}.md` con fuentes oficiales (reemplazan a la de AWS; Vercel es para frontend y funciones, no para una API con conexiones persistentes). Guía `docs/guides/deployment.md`.
- Un repositorio sin commits ya no bloquea un run que la política manda aislar: el contrato registra `isolation_waived: "no_commits"` (opcional, omitido en los demás contratos), mantiene las puertas humanas y `rapid start` lo avisa. Un repositorio con commits no cambia.

- Base de seguridad en todo proyecto: `templates/security/baseline.md` genera `.rapid-os/standards/security.md` con reglas imperativas, cada una con su estándar entre corchetes: OWASP ASVS 5.0.0 (L1 en MVP, L2 en Corporate), OWASP Top 10:2025 (A01-A10), OWASP API Security Top 10:2023 (API1-API10, solo stacks con API), NIST SSDF SP 800-218 (PO, PS, PW, RV), SLSA 1.2 (fijado de dependencias y acciones; Corporate añade Build L2 y Source L2) y CWE/CVSS v4.0. Los nombres salen de las fuentes oficiales y sus URL quedan en un comentario. Reemplaza `corporate/security.md`; `default-security.md` sigue sirviendo a `rapid start hardening` sin arquetipo. `mvp/coding-rules.md` ya no permite `any` y dice que la velocidad nunca rebaja la base. Página `docs/concepts/security-baseline.md`.
- Decisión `ai` del onboarding (`choose_ai`, después del arquetipo; `rapid setup set ai yes|no`): con `yes`, `security.md` incluye la sección de IA (OWASP Top 10 for LLM Applications 2025 y Top 10 for Agentic Applications 2026). `python-ai` y `nodejs-ai` no preguntan. Un `setup.json` sin el campo se lee como sin decidir mientras no esté terminado, y como `no` si lo está.
- CI de seguridad escrito por Rapid OS: al cerrar el onboarding de un repositorio vacío, `setup finish` escribe `.github/workflows/rapid-security.yml` desde `templates/ci/<python|typescript>-security.yml` (gitleaks, semgrep con las reglas OWASP Top 10, bandit o `pip-audit`/`npm audit`; Corporate añade SBOM y procedencia), con todas las acciones fijadas por SHA completo. No sobrescribe uno existente. Aparece en la salida de `finish` (`added_files` en `--json`) y se anuncia en `review_drafts` (`planned_files`).
- `rapid setup set archetype <id> --refresh` regenera `security.md` y `coding-rules.md` con copia `.bak`; `rapid doctor` avisa con `RAPID1421` (WARNING) si `security.md` no menciona ASVS. `rapid init` ya no reescribe un `security.md` hecho a mano.
- Modo hardening: la plantilla de spec incluye `findings` (`cwe`, `cvss_v4_vector`, `severity`, `standard_ref`) y la instrucción de clasificar cada hallazgo con CWE y CVSS v4.0 y de citar la regla de `security.md`. La spec solo conserva los campos de su esquema, por lo que el agente repite cada hallazgo en `acceptance_criteria`.
- Monolito modular como arquitectura de referencia: todo proyecto con backend (`python-api`, `python-ai`, `nodejs-ai`, `web-modern`) arranca con módulos por capacidad de negocio, capas dentro de cada módulo (`api`, `application`, `domain`, `infrastructure`), un único punto público por módulo y hexagonal solo donde se justifica. `rapid setup finish` y `rapid init` escriben `.rapid-os/standards/architecture.md` (la regla para el agente, con el árbol del stack, sin banner de supuesto) y `architecture.json` (la regla para Rapid OS); `docs-modern`, `frontend-creative` y `generic` no la reciben. Plantilla en `templates/architecture/modular-monolith.md`. Página `docs/concepts/architecture.md`.
- `rapid arch check [--json]`: verificador propio de la regla, sin dependencias nuevas (Python con `ast`, TypeScript/JavaScript con expresiones regulares). Informa una violación `RAPID1420` por capa que importa una capa que no le toca, módulo que importa algo distinto del punto público de otro, `shared` que importa un módulo o `domain` que importa una librería prohibida; exit 1 con violaciones, 0 sin ellas, sin módulos o (con aviso) sin `architecture.json`. En un proyecto existente solo juzga dentro de `modules_root`. El `__init__.py` de un módulo de Python solo puede estar vacío o reexportar su propio `public.py` (`init_reexport`): si no, `from app.modules.pagos import Repo` llegaba a una capa interna por el paquete. Solo los directorios de `modules_root` cuentan como módulos. En el worktree de un run (sin `.rapid-os/`), con una sesión activa cuyo contrato incluye `gate.architecture`, lee la regla del proyecto principal y analiza el código del directorio actual; si el run exige el gate y no hay regla, termina con `RAPID1420` y exit 1.
- Gate de máquina `gate.architecture` (tipo `architecture_check`, post-ejecución, no dispensable) en los contratos de `feature`, `bugfix` y `refactor` cuando existe `architecture.json`; `rapid next` propone `rapid check --gate gate.architecture -- rapid arch check` y `rapid finish` no da `PASS` sin él. `rapid check` ejecuta un `rapid` inicial como el Rapid OS en curso. El conjunto de reglas del evaluador no cambia, por lo que los reportes existentes conservan su digest.
- `docs/ARCHITECTURE.md` del onboarding exige las secciones `Módulos` y `Reglas de dependencia` (`RAPID1403` si faltan), con tres preguntas nuevas (capacidades de negocio, módulos hexagonales y reglas de dependencia) y `max_chars` de 6000; `/rapid-init` parte del monolito modular. La tarea de scaffold de un repositorio vacío pide la estructura de `architecture.md` (un módulo de ejemplo con sus cuatro capas y su punto público).
- `review_drafts`: antes de cerrar el onboarding la persona decide, documento por documento, si un borrador pasa a ser regla (`rapid setup doc <id> --confirm`) o queda como supuesto, con las dos consecuencias en el payload de la acción (`drafts`, `consequences`, `commands`). Nuevo subcomando `rapid setup review --done` (sin borradores sin confirmar, porque la persona los confirmó todos, termina con éxito sin cambiar nada; `RAPID1413` solo sin `--done`); `rapid setup finish` con la revisión pendiente es `RAPID1407`; `drafts_reviewed` en `setup.json` es opcional (un archivo anterior se lee como `false`). Un borrador nuevo o un `--reopen` reabre la revisión. `/rapid-init` resume cada borrador, ejecuta `--confirm` solo con una confirmación explícita y lista al final lo confirmado y lo que quedó como supuesto. Documentado en `project-docs.md` ("Confirmar o dejar como supuesto"), `cli.md` y `first-project.md`.
- Sidecar JSON por stack y topología (`templates/stacks/<id>.json`, `templates/topologies/<id>.json`) y módulo `rapid_os.domain.catalog` que los carga y valida (`RAPID1401`). `default_topology_for_stack` y la compatibilidad de `validate_stack_topology` leen ahora `compatible_topologies` y `default_topology`; el comportamiento de los 5 stacks existentes no cambia. Una plantilla sin sidecar es `RAPID1412` (aviso) y se trata como compatible con todas las topologías excepto `doc-site`.
- Stack `generic`: `rapid init` genera `tech-stack.md` con el lenguaje, gestor de paquetes, framework y testing detectados por el scanner y la regla de seguir las convenciones del repositorio. `infer_stack` lo reconoce por su línea de encabezado exacta (`# TECH STACK: GENERIC`).
- Bancos de preguntas como datos en `templates/setup/` (`docs/{brief,business,data-model,architecture}.json` y `stack-questions.json`), incluidos en sdist y wheel.

- `rapid setup next|show [--json]`: conductor de onboarding puro y de solo lectura (`rapid_os/domain/setup.py`, `rapid_os/orchestration/setup_conductor.py`, `rapid_os/adapters/setup_store.py`). Indica la siguiente decisión (stack, topología, arquetipo, agentes, comando de test, documentos, finish) y deriva el estado del disco en proyectos inicializados antes; nunca escribe, ni `.rapid-os/setup.json`. Códigos `RAPID1406` (estado inválido), `RAPID1413` (subcomando, clave o valor inválido) y, reservado, `RAPID1400` (INFO "Setup válido").

- Documentos del onboarding en el contexto con su procedencia: fuentes `doc.brief`, `doc.business`, `doc.data-model` y `doc.architecture` (solo cuentan con frontmatter `rapid-doc: <id>`), banner de supuestos para borradores sin confirmar, línea "pregunta, no inventes" para docs omitidos, y `doc.business` por encima de `standards/business.md` (`standard.business` pasa a omitido con la razón `superseded by doc.business`). Tipos de fuente aditivos `product` y `data_model`. `rapid validate` emite `RAPID1400`, `RAPID1403`, `RAPID1404`, `RAPID1406`, `RAPID1408` y `RAPID1410`. Página `docs/concepts/project-docs.md`.

- `rapid setup set|stack|doc|finish`: el harness completa el onboarding solo con comandos, y cada uno devuelve el siguiente `SetupAction` en `--json`. `set stack|topology|archetype|agents|test-command` registra la decisión (`RAPID1413` valor inválido, `RAPID1402` stack y topología incompatibles); `stack --custom --file -` guarda el `tech-stack.md` del harness con `Runtime`, `Framework` y `Testing` (`RAPID1409`); `doc <id> --source provided|drafted --file -` escribe `docs/<FILE>.md` con frontmatter (`rapid-doc`, `source`, `status`, `sha256`) y backup, valida secciones y tamaño solo para `drafted` (`RAPID1403`/`RAPID1404` son rechazo, `RAPID1405` un borrador sobre lo aportado por una persona sin `--replace`); `doc <id> --skip|--confirm|--reopen|--from-legacy`; `finish` (`RAPID1407` si quedan decisiones) aplica los estándares y la configuración, regenera los archivos de agente y es idempotente. `resolve_doc` de `business` incluye `legacy_source` cuando hay un `standards/business.md` con contenido y no existe `docs/BUSINESS_RULES.md`. Las escrituras viven en `rapid_os/orchestration/setup_apply.py`, sin `sys.exit`.
- `rapid init --business-file <ruta>` (importa las reglas de negocio como `provided`) y `rapid init --skip-docs`. Con `--yes` y sin ellos los documentos quedan `pending` y `init` termina con `Completa la documentación con /rapid-init o rapid setup next`.
- `RAPID1414` (WARNING): `rapid init` avisa, y `rapid doctor` reporta, que `rapid` no está en el `PATH` cuando hay shortcuts o hooks instalados. No cambia el exit code.

- `/rapid-init [descripción]` (`templates/shortcuts/rapid-init.md`): el agente conduce todo el onboarding con `rapid setup next --json` en bucle hasta `done`, propone con razones, redacta borradores que muestra completos, y solo ejecuta `--confirm` si la persona lo dice explícitamente. Es un shortcut de apoyo (no de modo); `rapid-init` encabeza `SHORTCUT_NAMES`.
- `rapid shortcuts install|list|remove --global --harness <id> [--only <shortcut>]`: instala en la carpeta de skills del usuario (`~/.claude/skills`, `~/.agents/skills`, `~/.cursor/skills`, `~/.gemini/config/skills`), con la documentación oficial citada en el código de cada adaptador. `vscode` no tiene ruta documentada: `--global` da `RAPID1413` y no escribe nada. `--only` limita el comando a un shortcut. `install.sh` e `install.ps1` ofrecen instalar `/rapid-init` global al terminar (solo con terminal interactiva, nunca por defecto).
- `rapid init` sugiere `/rapid-init` (`$rapid-init` en Codex) cuando quedan documentos pendientes.
- `rapid approve` con una tarea en curso imprime, tras `RAPID1014`, `<T> sigue en curso; espera a que el agente ejecute `rapid task done <T>`.` (mismo código y exit).
- Seed del brief: la acción `author_spec` de `rapid next` / `rapid start feature` (sin run ni spec) gana el campo opcional `seed` (`source`, `confirmed`, `stories[]` con todas las historias `- [ ] H001: ...` sin marcar y en orden, `business_doc`, `data_model_doc`), omitido si no hay brief administrado o no quedan historias. `/rapid-feature` propone la historia que conviene empezar y espera confirmación, copia las reglas relevantes de `docs/BUSINESS_RULES.md` a `business_rules` y etiqueta la spec con `story:<id>`; con un id (`H002`) usa esa historia.
- `rapid finish` (veredicto `pass` o `pass_with_waivers`) sugiere `Marca H002 como hecha en docs/PRODUCT_BRIEF.md` cuando la spec lleva el tag `story:H002`; nunca edita el brief (en `--json` la sugerencia va a stderr).
- Stack `python-api` (FastAPI, Pydantic v2, SQLAlchemy 2 async, Alembic, PostgreSQL, pytest + httpx; sin LangChain ni CrewAI), compatible con `fullstack-separated` (por defecto) y `fullstack-baas`. `infer_stack` lo reconoce por `TECH STACK: PYTHON API`. `python-ai` queda solo para «agentes de IA y pipelines de datos».
- Proyecto nuevo (sin código fuente fuera de `docs/` y carpetas ocultas, y sin tests): `rapid start feature` añade como primera tarea `T001: Scaffold mínimo con un test que pase` (las tareas escritas se renumeran para coincidir con los ids del contrato) y crea el contrato sin `gate.baseline`, con el campo opcional `baseline_waived: "empty_repository"` (omitido del contenido canónico y del digest de todos los demás contratos). `rapid start` avisa de la renumeración en el campo opcional `notes` de su salida (`T001→T002`; `Nota: ...` en texto) y `/rapid-feature` se la explica a la persona. `rapid status` y `rapid finish` muestran `Sin baseline: proyecto nuevo`. `bugfix`, `refactor` y `hardening` fallan en un repositorio nuevo con `RAPID1413` (`No hay código que arreglar|refactorizar|endurecer; usa /rapid-feature`). Un repo con código y sin tests conserva la baseline, y `run_baseline` sugiere crear un test que pase o usar `research`.

### Changed
- Documentación de entrada con comandos ligeros: la portada, Primeros pasos, Tu primer proyecto, Proyecto existente y los cinco laboratorios por modo enseñan solo instalar, `/rapid-init`, `/rapid-<modo>`, `rapid approve` y `/rapid-next`. Los comandos v3 quedan plegados en «Modo avanzado» (no se borra nada). El laboratorio «Primer Proyecto Gobernado» pasa al final como «Bajo el capó» (nivel Avanzado) y el primero es Feature. Nuevo contrato `test_beginner_routes_only_show_light_commands`: en esas rutas ningún comando lleva más de dos flags.
- Sección «Primeros pasos» como ruta de aprendizaje en seis páginas, en orden de lectura: Tu primer proyecto, Un proyecto que ya existe, Cuando el agente se detiene (nueva: aprobar, rechazar, dispensar, ver el estado, cancelar y leer el veredicto), Cómo se escribe la spec, Qué sabe el agente de tu proyecto y Próximos pasos. Las cuatro últimas explican primero en lenguaje llano y pliegan los comandos v3; «Próximos pasos» ya no termina en el ciclo de 8 fases, sino en laboratorios, qué modo usar, trabajo en equipo y diagnósticos.
- Sin comandos pesados en las páginas de aprendizaje (portada, Primeros pasos, Laboratorios, Instalación y guía de shortcuts), ni siquiera plegados: los laboratorios por modo dejan solo la ruta con shortcuts, el estado inicial y los requisitos; el recorrido con comandos v3 vive en un único sitio, el recorrido manual «Bajo el capó» (sección Cómo funciona), cuyos comandos se reescribieron con a lo sumo dos flags (`rapid init --stack python-ai --yes` + `rapid setup set test-command`, `rapid spec create --title … --task …` + `rapid spec status <id> ready`) y siguen siendo ejecutables (`test_tutorial_executable`). Contrato nuevo `test_learning_pages_never_show_heavy_commands`.
- `install.sh` e `install.ps1`: la pregunta final instala todos los shortcuts a nivel usuario (`rapid shortcuts install --global --harness <id>`), no solo `/rapid-init`, para que `/rapid-feature` y los demás existan al cerrar el onboarding sin otro comando.
- Los ids de stack `python-api`, `python-ai`, `nodejs-ai`, `web-modern` y `frontend-creative` ya no son plantillas: son alias de los stacks por componente. Con la topología `fullstack-separated`, `rapid setup set stack python-api` llena solo el backend y el frontend se elige aparte. `fullstack-baas` ya no admite un stack de backend (sus componentes son `frontend` y `baas`). `choose_stack` siempre trae `questions` e `instruction`.
- `rapid deploy --target <plataforma>` (o el argumento posicional) ya no escribe `DEPLOY.md`: imprime la plantilla y `rapid setup doc deployment --reopen`; una plataforma desconocida es `RAPID1413`.
- Los archivos de agente que Rapid OS regenera (`CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `INSTRUCTIONS.md`, `.agent/rules/constitution.md`) ya no dejan `<archivo>.<timestamp>.bak` en la raíz: la copia anterior va a `.rapid-os/backups/`, solo si el contenido cambió, con las 5 más recientes por archivo. `rapid init` y `rapid setup finish` añaden `.rapid-os/backups/` al `.gitignore`.
- Los shortcuts de modo y `rapid-approve` piden aprobación solo cuando `action.kind` es `await_human_approval` (`awaiting_human` lista los gates humanos desde el inicio del run), dan el comando exacto con el id del gate para ejecutarlo en otra terminal y ya no sugieren el prefijo `!`.
- `rapid init` usa el mismo estado y la misma lógica de escritura que `rapid setup` (escribe `.rapid-os/setup.json`). La sección de negocio pasa a ser una por documento (brief, negocio, modelo de datos, arquitectura) con cuatro opciones: importar un archivo, escribirlo en la terminal, dejarlo para el agente u omitirlo; sin entrada adicional el documento queda pendiente. Se elimina el andamiaje `TODO` de `docs/` (`create_optional_docs_scaffold`, `SPECS.md`) y `rapid init` ya no escribe `standards/business.md` ni guarda plantillas de negocio. Corrige que, tras responder que sí a "¿Importar archivo?", una ruta vacía o un directorio daba `Is a directory`: ahora vuelve a preguntar.

## [3.1.0] - 2026-10-18

### Added
- **Porcelain layer**: `rapid start`, `rapid next`, `rapid check`, `rapid task`, `rapid attach`, `rapid finish`, `rapid approve`, `rapid status` and `rapid abort` drive a governed run on top of the v3 plumbing. A pure Conductor (`next_action`) asks the `BehavioralEvaluator` what is missing and returns a `NextAction`; the active run lives in `.rapid-os/session.json`. Evidence producers: `rapid:check`, `rapid:start`, `rapid:finish`, `rapid:attach`.
- **Behavioral ruleset v2**: `rapid check --expect fail --task <id>` records an expected failure (`expectation: "fail"`) that produces a `reproduction.<task>` assertion and does not count as a failing task or gate evidence (`RAPID1320`); review evidence produced by a `harness:*` producer cannot close a human gate.
- **Five engineering modes** with playbooks in `templates/modes/`: `feature`, `bugfix` (baseline before the red test, `check --expect fail` on `T001`), `refactor` (blocked when passing tests drop below the baseline), `hardening` (isolated git worktree with `rapid start --worktree`) and `research` (`rapid attach`, no mandatory tests).
- **Shortcuts**: `rapid shortcuts install|list|remove` and `rapid init --shortcuts` generate eight `/rapid-<mode>` shortcuts (`rapid-feature`, `-bugfix`, `-refactor`, `-hardening`, `-research`, `-next`, `-status`, `-approve`) for Claude Code, Codex, Antigravity, Cursor and VS Code from `templates/shortcuts/`, idempotent and with `.bak` backups (`RAPID1311`–`RAPID1318`). A `RAPID1321` warning flags harness selections that leave the same shortcut in two folders one tool reads.
- **Claude Code hooks**: `rapid hook stop|pre-tool` keep the agent working until a person is needed and deny reserved commands (`rapid approve`, `rapid abort`, `rapid run gate`, `rapid evidence add`) and edits inside `.rapid-os/`; installed with `rapid shortcuts install --hooks` or `rapid init --hooks` (`RAPID1337`–`RAPID1339`).
- `rapid approve` without arguments lists pending human gates; `--waive` (waivable gates only) and `--reject` (review outcome `changes_requested`) with `--reason`; `--reviewer` defaults to `git config user.name` (`RAPID1330`–`RAPID1336`).
- `docs/architecture/orchestration.md` and `docs/guides/shortcuts.md`.

### Changed
- **`rapid approve` hardened**: it requires a TTY, refuses `CLAUDE_CODE_CHILD_SESSION=1` and, new, refuses when any ancestor process is Claude Code (`RAPID1310`; `RAPID1319` in `rapid doctor` when the ancestry cannot be read). The ancestry check is best-effort: a process that detaches from its parent (double fork, `setsid`, `nohup … &`), a renamed `claude.exe` or a reused pid escape it. The rule is unchanged: a person approves in their own terminal.
- **Shortcuts JSON contract**: in `rapid shortcuts install --json` and `list --json`, `warnings` is a list of homogeneous objects `{code, message, ...}` (`RAPID1315`, `RAPID1316`, `RAPID1321`); the loose text warnings of `install --json` became objects with the same text in `message`.
- Package version is `3.1.0`; the installers and the installation docs resolve the `v3.1.0` tag.
- `rapid finish` on a run that already ended exits `0` only when the stored verdict is `pass` or `pass_with_waivers` and records no new evidence; a run without a report exits `1` with `already ended (<outcome>)`.
- Product boundaries now state what is executed: the plumbing runs nothing; the porcelain runs only the `test_command` of `.rapid-os/config.json` or the argv given to `rapid check`, creates a worktree only with `rapid start --worktree`, and never invokes agents or approves human gates.
- Documentation presents the shortcuts as the main flow and the v3 commands as advanced mode; new "Shortcuts y orquestación" sidebar category and navbar entry; the unused `site/` Docusaurus template was removed.

### Fixed
- `rapid finish` text mode no longer fails with `AttributeError` and prints the report revision and verdict.
- Runs without a baseline gate (low-risk spikes) and isolated runs could never leave `prepared`.
- `rapid finish` no longer attributes to the run the untracked files that existed before `rapid start`.
- `rapid init --yes` without a scanner suggestion no longer picks the alphabetically first topology (`doc-site`) for every stack: the default topology is coherent with the stack (`doc-site` only with `docs-modern`, and `docs-modern` always with `doc-site`), so `rapid validate` no longer fails with `RAPID402`/`RAPID403`.
- `rapid init` (also with `--yes`) creates `.rapid-os/standards/security.md` from a minimal template when it does not exist, so `rapid start hardening` can create the run; the `RAPID1004` message now names the missing file and how to create it.
- `rapid start --spec-file` reuses a spec with the same identity and content when a previous start failed after creating it; with different content it exits with `RAPID1322` and suggests `rapid start <mode> --spec <id>` instead of an error without guidance.
- The `feature` playbook's `author_spec` instruction now says `rapid start <modo> --spec-file -` instead of `rapid spec create`.
- `rapid next` returns `blocked` with `rapid start --resume --worktree` when the contract requires an isolated workspace and the session has no worktree yet, like `rapid start`.
- `rapid start` and `rapid approve` report expected failures (a missing context source, a closed stdin) with a RAPID code instead of a traceback.

### Security & Hardening
- Defense in depth around human approval: TTY, session marker, process ancestry, typed confirmation, optional Claude Code hooks (including a guard against clearing the session variables) and `user`-only review evidence. These are best-effort controls, not cryptographic attestation.
